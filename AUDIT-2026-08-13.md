# Rapport d’audit de blink2video.py

Date de l’audit : 13 août 2026  
Fuseau : Europe/Paris  
Révision auditée : 58f5566  
Périmètre principal : blink2video.py  
Périmètre connexe nécessaire : runtime.py, serve.py, merge_daily.py, watch.py,
tests.py, smoketest.py, blink2video.spec  
Environnement d’inspection : Python 3.12.0, blinkpy 0.25.9, aiohttp 3.14.3

## 1. Objet du rapport

Ce document conserve l’analyse détaillée de blink2video.py et transforme ses
conclusions en programme de travail progressif.

Les objectifs sont :

1. corriger les erreurs pouvant provoquer un arrêt, une corruption silencieuse,
   une perte d’état ou un processus orphelin ;
2. garantir chaque correction par un test de non-régression isolé ;
3. mesurer les performances avant toute modification ;
4. vérifier après chaque étape que les coûts ont diminué ou, à défaut, qu’aucune
   régression mesurable n’a été introduite ;
5. ne passer à l’étape suivante qu’après satisfaction de critères de sortie
   explicites ;
6. consigner, pour chaque étape réellement terminée, le travail effectué, les
   tests exécutés, les valeurs mesurées, les écarts au plan et le verdict.

Le rapport décrit un plan. Aucune correction de production n’a été appliquée
pendant l’audit.

## 2. Résumé exécutif

Le fichier est lisible, très commenté et possède plusieurs bonnes fondations :

- téléchargement vers un fichier partiel puis renommage ;
- normalisation des dates en UTC ;
- sauvegarde atomique envisagée pour les fichiers JSON ;
- poursuite du lot après l’échec isolé d’un clip ;
- séparation des gros verbes délégués dans des modules distincts ;
- volonté explicite de préserver les clips et les exclusions.

La configuration recommandée, blink2video start, met cependant plusieurs
processus en concurrence. Les mécanismes actuels ne garantissent pas les
invariants annoncés par le code.

Les cinq invariants à rétablir en premier sont :

1. une collection vide est un succès vide, jamais une erreur de type ;
2. un fichier déclaré téléchargé est réellement une vidéo complète ;
3. un événement déjà acquis reste acquis après renumérotation distante ;
4. une décision plus récente, notamment une exclusion, ne peut pas être écrasée
   par une copie d’état plus ancienne ;
5. une ressource verrouillée ne peut être utilisée que par un propriétaire à la
   fois.

La prochaine release devrait être bloquée tant que les anomalies B-01 à B-06 ne
sont pas corrigées et couvertes.

Une évolution fonctionnelle a été ajoutée au périmètre après l’audit :

- lancer blink2video sans argument doit être équivalent à blink2video start ;
- le démarrage doit d’abord vérifier réellement l’authentification ;
- si elle manque ou n’est plus valide, une page locale de connexion doit
  s’ouvrir dans le navigateur ;
- le formulaire doit gérer les identifiants et la vérification en deux étapes ;
- un premier contrôle read-only de type list ou mini-smoke doit confirmer que
  la session et le compte fonctionnent ;
- les boucles permanentes ne doivent être lancées qu’après ce contrôle.

## 3. Méthode et limites

### 3.1 Travail effectué

L’audit a comporté :

- lecture intégrale des 1 064 lignes de blink2video.py ;
- cartographie de ses appels à runtime.py, serve.py, merge_daily.py et watch.py ;
- lecture de tests.py et smoketest.py ;
- inspection de la version de blinkpy installée ;
- analyse AST ;
- analyse Ruff sans correction automatique ;
- sondes ciblées en mémoire ou dans des dossiers temporaires ;
- revue séparée des chemins téléchargement, CLI/processus et couverture.

### 3.2 Défauts reproduits sans compte Blink

Les comportements suivants ont été reproduits :

- manifeste cloud vide : TypeError lors du déballage du résultat ;
- option --since 0 : requête portant sur 30 jours ;
- option --loop -1 : valeur acceptée ;
- port 70000 pour open : OverflowError brut ;
- noms A/B et A_B : même safe_name ;
- download --camera watch : watch est interprété comme un nouveau verbe ;
- JSON racine de mauvais type : AttributeError ;
- fusion d’un état périmé : suppression du drapeau excluded.

### 3.3 Limites

L’audit n’a pas utilisé d’identifiants Blink, de caméra ni de Sync Module. Les
interactions réelles avec le service devront être validées dans un test manuel
optionnel, jamais dans la CI.

La suite complète tests.py n’a pas été exécutée pendant cette phase de lecture
seule, car elle peut envoyer une notification système et écrire des états dans
le dossier applicatif réel.

## 5. Échelle de priorité

- B : bloquant. Crash fréquent, corruption silencieuse, perte d’une décision
  utilisateur ou exclusion mutuelle non garantie.
- I : important. Fiabilité dégradée, comportement incohérent, sécurité ou
  portabilité insuffisante.

## 6. Anomalies bloquantes

### B-01 — Contrat de retour cassé sur un cloud vide

Emplacements :

- blink2video.py:602, traiter_cloud ;
- blink2video.py:613–614, retour False ;
- blink2video.py:806–809, déballage de deux valeurs.

Quand le cloud est vide ou que le filtre de caméra ne retient rien,
traiter_cloud renvoie un booléen seul. L’appelant attend toujours
erreur_cloud, nouveaux_cloud.

Conséquences :

- TypeError ;
- arrêt de list avec la source all ;
- arrêt de download --from cloud ;
- mort définitive de la boucle cloud de start.

Correction attendue :

- un type de retour unique ;
- idéalement un résultat nommé contenant téléchargés, adoptés, ignorés et
  échecs ;
- à court terme, retourner systématiquement un tuple.

Test de non-régression : T-B01.

### B-02 — Corps HTTP d’erreur enregistré comme MP4

Emplacements :

- blink2video.py:260–271, CloudClip.download_to ;
- blink2video.py:646–650, renommage et inscription au registre.

Le statut HTTP n’est jamais contrôlé. Tout corps non vide est accepté. Une
réponse 401, 404, 429 ou 500 contenant du JSON ou du HTML peut donc devenir un
fichier .mp4 et être inscrite comme téléchargement réussi.

Conséquences :

- corruption silencieuse ;
- erreur découverte seulement pendant l’assemblage ;
- fichier durablement considéré comme acquis.

Correction attendue :

- exiger un statut de succès ;
- distinguer les erreurs transitoires des erreurs définitives ;
- écrire le corps par blocs ;
- vérifier la taille annoncée si elle existe ;
- vérifier au minimum la boîte MP4 ftyp ou effectuer un probe vidéo ;
- ne renommer et ne committer le registre qu’après validation.

Tests : T-B02-200, T-B02-401, T-B02-404, T-B02-429, T-B02-500,
T-B02-TRUNCATED.

Benchmarks : P-06 et P-07.

### B-03 — Réindexation USB suivie d’un retéléchargement

Emplacements :

- blink2video.py:372–378, target_path ;
- blink2video.py:451–464, state_key ;
- blink2video.py:485–501, is_downloaded.

La clé d’état ignore clip.id afin de survivre à une réindexation, mais le nom de
fichier contient clip.id. Après une réindexation :

1. la clé d’état reste la même ;
2. le chemin recalculé change ;
3. is_downloaded ne consulte pas entry.path ;
4. le nouveau chemin est absent ;
5. le même clip est téléchargé une seconde fois.

Conséquences :

- doublons en masse ;
- espace disque gaspillé ;
- ancien fichier orphelin ;
- promesse du README non tenue.

Correction attendue :

- faire de entry.path l’autorité pour un acquis existant ;
- séparer identité distante, identité d’événement et nom de fichier ;
- prévoir une migration de registre versionnée.

Tests : T-B03-REINDEX, T-B03-MISSING, T-B03-EXCLUDED.

Benchmark : P-04.

### B-04 — Une sauvegarde périmée peut annuler une exclusion

Emplacements :

- blink2video.py:417–448, save_download_state et _ecrire_registre ;
- merge_daily.py:455–463, écriture d’une exclusion.

Le registre est verrouillé au moment de l’écriture, mais le downloader détient
une copie complète chargée auparavant. _ecrire_registre relit le disque puis
applique clips.update avec la copie ancienne.

Scénario :

1. A charge le registre ;
2. B pose excluded=True et sauvegarde ;
3. A ajoute un autre clip ;
4. A sauvegarde sa copie ;
5. la version non exclue de A remplace la décision de B.

Conséquences :

- perte d’une action explicite de l’utilisateur ;
- clip exclu susceptible d’être téléchargé à nouveau ;
- incohérence entre Blink_Excluded et le registre.

Correction attendue :

- transaction unique couvrant lecture, décision et écriture ;
- mise à jour par delta et non par copie complète ;
- protection forte des tombstones ;
- recommandation : stockage transactionnel SQLite en mode WAL.

Tests : T-B04-INTERLEAVE, T-B04-TOMBSTONE, T-B04-CRASH.

Benchmarks : P-02 et P-03.

### B-05 — Verrou interprocessus non atomique et volé après dix minutes

Emplacements :

- runtime.py:491–541, verrou ;
- blink2video.py:719–723, verrou download ;
- blink2video.py:431, verrou registre.

Le protocole actuel lit le fichier, conclut qu’il est libre, puis l’écrit. Deux
processus peuvent effectuer les deux premières opérations simultanément et
entrer tous les deux.

Un verrou plus vieux que stale_after est en outre considéré périmé même si son
PID est vivant. Le téléchargement conserve son verrou sur un passage complet,
qui peut durer plus de dix minutes.

Conséquences :

- deux écrivains sur le même .part ;
- deux mises à jour concurrentes du registre ;
- assemblages concurrents ;
- suppression possible du verrou du voisin.

Correction attendue :

- verrou OS ou création exclusive atomique ;
- jeton UUID propre à l’acquisition ;
- identité du processus incluant son heure de création ;
- ne jamais expirer un propriétaire vivant sur le seul critère du temps ;
- heartbeat si une lease temporelle reste nécessaire.

Tests : T-B05-RACE20, T-B05-LONG, T-B05-CRASH, T-B05-PID-REUSE.

Benchmark : P-08.

### B-06 — Le téléchargement USB ne réserve pas le Sync Module

Emplacements :

- blink2video.py:34–36, hub_lock ;
- blink2video.py:736–805, parcours USB ;
- serve.py:833 et serve.py:1149, verrou pris par le direct et l’actualisation.

Le downloader prend le verrou download, mais jamais le verrou hub partagé avec
le direct. Un direct peut donc commencer pendant la fabrication du manifeste,
prepare_download ou download_video.

Conséquences :

- réponses System is busy ;
- échecs intermittents ;
- retries coûteux ;
- fiabilité dépendante du hasard de planification.

Correction attendue :

- verrou par sync_id ;
- section limitée aux opérations qui utilisent réellement le module ;
- aucune réservation du hub pour le cloud ;
- éviter les verrous imbriqués non réentrants dans serve.

Tests : T-B06-DIRECT-USB, T-B06-HUBS-DISTINCTS, T-B06-CLOUD-INDEPENDANT.

Benchmark : P-09.

## 7. Anomalies importantes

### I-01 — CONFIG et OUTPUT ignorent BLINK_HOME

Emplacements :

- blink2video.py:26–27 ;
- runtime.py:206–216 ;
- blink2video.py:994 et 1008.

Les chemins par défaut sont relatifs au répertoire courant. Une commande simple
et la même commande composée ne travaillent donc pas nécessairement au même
endroit.

Risques :

- refresh token déposé dans un autre projet ;
- clips écrits ailleurs ;
- serveur ne voyant pas la session créée en CLI ;
- contradiction avec le README.

### I-02 — Sauvegardes d’authentification concurrentes

Emplacements :

- blink2video.py:157–164 ;
- runtime.py:62–66, composition start.

Toutes les sessions emploient blink_auth.tmp sans verrou. Plusieurs clients
peuvent remplacer le même temporaire ou écraser un token plus récent.

Le temporaire blink_auth.tmp n’est pas couvert par les motifs actuels du
.gitignore.

### I-03 — Tokens rafraîchis non persistés

Emplacement : blink2video.py:88–92.

make_blink ne fournit pas de callback de persistance à Auth. Une session longue
peut rafraîchir son token uniquement en mémoire. Après un crash, le disque peut
contenir une version ancienne.

### I-04 — Déduplication asymétrique USB/cloud

Emplacements :

- blink2video.py:300–326, rapprocher ;
- blink2video.py:620–624, emploi côté cloud ;
- blink2video.py:756–764, absence d’équivalent côté USB.

Si l’USB arrive avant le cloud, le cloud est rapproché. Si le cloud arrive avant
l’USB, l’USB retélécharge l’événement.

### I-05 — Fichier cloud absent impossible à réparer

Emplacements : blink2video.py:620–638.

Toutes les entrées du registre participent au rapprochement, même si leur
fichier est absent ou vide. --overwrite intervient trop tard pour changer cette
décision.

Une absence accidentelle doit entraîner une réparation. Seule une tombstone
excluded doit interdire le téléchargement.

### I-06 — Manifeste privé, cumulatif et manifest_id potentiellement périmé

Emplacements :

- blink2video.py:209–231 ;
- blink2video.py:391–392.

Le code dépend de sync._local_storage, interface privée de blinkpy. Dans la
version inspectée, le manifeste est un SortedSet conservé entre les mises à
jour. Les objets déjà présents peuvent conserver leur ancien manifest_id.

L’adaptateur du projet doit produire son propre snapshot frais et actualiser
l’adresse de chaque item.

### I-07 — --since 0 devient 30 jours

Emplacement : blink2video.py:281.

since_days or 30 confond zéro et absence de valeur. Le chemin USB traite zéro
comme un cutoff immédiat, le cloud comme 30 jours.

### I-08 — Pagination cloud plafonnée et coûteuse

Emplacements : blink2video.py:281–284.

stop=20 correspond à 19 pages dans blinkpy 0.25.9, soit approximativement 475
éléments si une page en contient 25. Les mêmes pages peuvent être relues chaque
minute.

Risques :

- clips anciens jamais vus dans une fenêtre très active ;
- centaines ou milliers de requêtes quotidiennes inutiles ;
- latence proportionnelle à 30 jours d’historique plutôt qu’aux nouveautés.

### I-09 — Compte sans Sync Module refusé

Emplacements : blink2video.py:690–705.

main exige blink.sync avant même de terminer login ou de considérer une source
cloud. Cela contredit l’indépendance annoncée du cloud et l’existence de
_HubCloud.

### I-10 — JSON valide mais schéma invalide non géré

Emplacements :

- blink2video.py:59–77 ;
- blink2video.py:402–414 ;
- blink2video.py:622–676 ;
- runtime.py:516–527 ;
- runtime.py:288–303.

Les lecteurs supposent trop tôt un dictionnaire et des champs convertibles. Une
racine [], null, une entrée de clip non dictionnaire ou une date invalide peut
faire échouer toute la commande.

### I-11 — Valeur d’option confondue avec un verbe

Emplacement : runtime.py:652–674.

Toute chaîne égale à un verbe ouvre un nouveau groupe. Les guillemets ne
changent rien, car le shell les retire avant Python.

Exemples problématiques :

    blink2video download --camera watch
    blink2video download --camera update
    blink2video watch --ignore serve

Le second exemple peut aller jusqu’à lancer une mise à jour non demandée après
l’échec du premier groupe.

### I-12 — Boucles non validées et classification textuelle

Emplacements :

- runtime.py:677–686 ;
- blink2video.py:727–729 ;
- blink2video.py:987.

Problèmes :

- valeur négative acceptée ;
- zéro signifie une exécution ;
- --loop=1 n’est pas détecté comme persistant ;
- comportements différents entre asyncio.sleep et time.sleep ;
- risque de boucle serrée contre l’API.

### I-13 — Supervision incomplète

Emplacements :

- blink2video.py:969–1038 ;
- runtime.py:264–340.

Cas non couverts :

- download --loop seul non inscrit ;
- enfant ponctuel non inscrit ;
- exception pendant les démarrages ;
- Ctrl+C avant l’entrée dans le bloc de nettoyage ;
- descendants ffmpeg non arrêtés ;
- absence de wait après terminate ;
- fiche supprimée alors qu’un enfant vit ;
- enfant qui termine avant la première itération de surveillance.

### I-14 — stop peut perdre sa cible ou viser un PID recyclé

Emplacements :

- blink2video.py:905–928 ;
- runtime.py:233–303.

La fiche est supprimée avant confirmation de la mort. L’identité du processus
est limitée au PID ; l’heure enregistrée dans la fiche n’est jamais comparée à
l’heure de création fournie par le système.

### I-15 — Contrôle d’intégrité limité à une taille non nulle

Emplacements :

- blink2video.py:383–384 ;
- blink2video.py:485–501 ;
- blink2video.py:638–642 ;
- blink2video.py:760–762.

Un fichier d’un octet est considéré complet. Le champ bytes enregistré dans le
registre n’est jamais utilisé pour vérifier le fichier.

### I-16 — Collisions de noms et composants de chemin non bornés

Emplacements : blink2video.py:366–378.

safe_name transforme des noms distincts en une même chaîne. Les noms réservés
Windows, la longueur maximale et clip.id ne sont pas normalisés. Une valeur API
inattendue peut créer un chemin invalide ou sortir de l’organisation prévue.

### I-17 — Erreurs transitoires non contenues

Emplacements :

- blink2video.py:714–729 ;
- blink2video.py:738–743 ;
- blink2video.py:806–809.

boucler ne capture que BusyError. Une panne HTTP, une erreur d’authentification
ou un changement de schéma peut tuer définitivement une boucle de fond.

Il faut distinguer :

- succès vide ;
- réponse partielle ;
- indisponibilité transitoire ;
- authentification à renouveler ;
- erreur de données définitive.

### I-18 — Compteurs cloud incorrects

Emplacements : blink2video.py:638–661.

Un fichier déjà présent mais adopté dans le registre est inclus dans
len(inedits) - echecs et peut être annoncé comme nouveau téléchargement.

### I-19 — Aide de --overwrite non conforme

Emplacements :

- blink2video.py:580 ;
- blink2video.py:758–764 ;
- blink2video.py:621–638.

L’aide parle de remplacer les fichiers de taille différente. Le chemin USB
retélécharge en pratique tout ce qui est sélectionné avec --overwrite. Le cloud
peut au contraire ne rien remplacer si le registre contient déjà l’événement.

Les notions repair, overwrite et force doivent être définies séparément.

### I-20 — Identité cloud liée arbitrairement au premier module

Emplacement : blink2video.py:630–668.

Le premier Sync Module sélectionné est utilisé pour former les clés de tous les
clips cloud. Sur un compte multi-réseaux, clip.network_id est l’identité plus
pertinente.

### I-21 — Matching temporel non bijectif

Emplacements : blink2video.py:312–325.

Plusieurs clips cloud peuvent être classés comme doublons du même clip local.
Le rapprochement doit consommer un match et employer un identifiant stable de
caméra.

### I-22 — Port open non validé et serveur non identifié

Emplacements : blink2video.py:870–884.

Un port hors plage produit une trace brute. Toute socket locale ouverte est
considérée comme l’interface blink2video, sans endpoint de santé ni version.

## 7.1 Évolution fonctionnelle demandée

### E-01 — Démarrage sans argument et onboarding web

Comportement actuel :

- blink2video sans argument affiche l’aide et se termine ;
- start lance directement plusieurs processus ;
- en l’absence de session, plusieurs consommateurs peuvent tenter de se
  connecter ou rester sans authentification ;
- /api/status vérifie principalement la présence du fichier, pas la validité de
  la session ;
- serve.py possède déjà LoginFlow, /api/login, /api/2fa et une boîte de dialogue
  de connexion réutilisables.

Comportement cible :

1. blink2video et blink2video start appellent exactement le même parcours ;
2. --help et --version conservent leur sens et ne démarrent rien ;
3. un unique processus propriétaire exécute le préflight ;
4. la session sauvegardée est testée sans interaction ;
5. si elle est valide, le parcours continue sans ouvrir le navigateur ;
6. si elle est absente ou invalide, un serveur local limité à 127.0.0.1 expose
   la page de connexion ;
7. le navigateur s’ouvre sur cette page ; si cela échoue, l’URL est affichée ;
8. l’e-mail, le mot de passe et le code 2FA sont traités dans ce processus
   unique ;
9. le mot de passe n’est ni écrit, ni journalisé, ni conservé après le flux ;
10. après succès, un mini-smoke read-only vérifie le compte ;
11. le résultat du contrôle est affiché dans la page et le terminal ;
12. les processus de start ne sont créés qu’après succès ;
13. en cas d’échec ou d’annulation, aucune boucle de fond n’est laissée.

Le mini-smoke recommandé réutilise la logique métier de list mais expose un
résultat structuré :

- refresh/authentification réussie ;
- homescreen du compte lisible ;
- inventaire des réseaux, Sync Modules et caméras lisible ;
- compte cloud-only accepté ;
- aucun direct, armement, manifeste USB ou téléchargement déclenché.

Sécurité minimale de la page :

- écoute loopback uniquement ;
- jeton CSRF aléatoire et à usage court ;
- une seule tentative active à la fois ;
- réponses no-store ;
- aucun identifiant dans les logs ;
- délai d’expiration et bouton d’annulation ;
- limitation des tentatives ;
- fermeture de la session temporaire après succès ou abandon.

Cette évolution est planifiée à l’étape 5, après la stabilisation du magasin
d’authentification et avant le refactor général de la CLI.

## 8. Optimisations et améliorations structurelles

### O-01 — Téléchargement cloud entièrement en mémoire

Emplacement : blink2video.py:264–270.

Le corps entier est lu avant Path.write_bytes. Le streaming par blocs permet :

- mémoire bornée ;
- suivi de progression ;
- taille et hash au fil de l’eau ;
- reprise ou nettoyage plus simples.

### O-02 — Réécriture complète du JSON après chaque clip

Emplacements : blink2video.py:788–794 et 648–650.

Chaque succès relit et sérialise la totalité du registre. Un lot de N clips peut
ainsi approcher un coût quadratique.

### O-03 — Rapprochement temporel quadratique

Emplacements : blink2video.py:312–325.

Pour chaque clip cloud, toutes les dates de la caméra sont parcourues. Un index
trié avec bisect ou un index SQL réduit ce coût.

### O-04 — Scan cloud sans watermark

Emplacements : blink2video.py:274–297.

Une boucle à la minute relit jusqu’à 30 jours. Un watermark durable avec
recouvrement réduit les appels tout en protégeant contre les arrivées tardives.

### O-05 — Cadence qui dérive

Emplacements : blink2video.py:727–729 et runtime.py:689–706.

Le sommeil commence après le travail. Une opération de quatre minutes avec une
cadence de cinq minutes démarre en réalité toutes les neuf minutes. Une
échéance fondée sur time.monotonic évite cette dérive.

### O-06 — Bootstrap trop précoce

Emplacements : blink2video.py:14–23 et runtime.py:136–198.

Le bootstrap s’exécute avant de savoir si la commande est help, stop, open,
update ou un verbe Blink. Une installation cassée peut rendre stop inutilisable
et une simple aide peut créer un environnement ou contacter PyPI.

### O-07 — Dépendances non contraintes

Emplacements :

- runtime.py:127–133 ;
- build.py:33 ;
- workflows CI et release.

## 10. Architecture cible

La cible proposée reste une application locale, sans service externe ajouté.

### 10.1 Parcours de démarrage convivial

Le point d’entrée suit une machine d’état explicite :

    invocation
      → préflight d’authentification
      → session valide ?
          oui → mini-smoke read-only
          non → serveur d’onboarding local
                  → formulaire identifiants
                  → formulaire 2FA si demandé
                  → sauvegarde de session
                  → mini-smoke read-only
      → préflight réussi ?
          oui → lancement de la composition standard
          non → diagnostic, aucune boucle lancée

Le serveur d’onboarding peut réutiliser les composants de serve.py, mais le
flux d’authentification doit vivre dans un module indépendant afin que le
lanceur ne dépende pas du serveur complet.

### 10.2 Racine de données unique

Tous les chemins applicatifs dérivent d’une seule racine :

- BLINK_HOME si défini ;
- sinon le dossier de données documenté.

La racine contient authentification, médias, base d’état, verrous, journaux et
fiches de processus. Le CWD ne change jamais leur emplacement.

### 10.3 Modèle de clip explicite

Un clip porte séparément :

- source : usb ou cloud ;
- compte et réseau ;
- identifiant stable de caméra ;
- nom d’affichage ;
- identifiant distant ;
- instant UTC ;
- chemin local ;
- taille et éventuellement hash ;
- statut ;
- provenance corrélée ;
- état excluded.

### 10.4 Persistance transactionnelle

SQLite WAL est recommandé pour :

- transactions multi-processus ;
- contraintes uniques ;
- index temporels ;
- claims de téléchargement ;
- tombstones protégées ;
- curseurs de pagination ;
- mises à jour partielles ;
- migrations versionnées.

Le JSON peut rester un format d’export et de diagnostic.

### 10.5 Adaptateurs de sources

Un adaptateur USB encapsule toute dépendance aux détails privés de blinkpy.
Un adaptateur cloud gère pagination, watermark et réponses HTTP. Le reste du
programme manipule le même modèle de clip.

### 10.6 Superviseur unique

Le superviseur :

- parse toute la commande avant tout effet ;
- connaît le cycle de vie de chaque verbe ;
- enregistre tous les enfants ;
- utilise groupes POSIX ou Job Objects Windows ;
- arrête, attend puis force si nécessaire ;
- conserve la fiche tant qu’un processus survit.

## 11. Règles communes à toutes les étapes

Chaque étape suit la séquence suivante :

1. écrire ou sélectionner les tests qui échouent sur la version précédente ;
2. enregistrer le baseline des benchmarks concernés ;
3. effectuer uniquement les changements de l’étape ;
4. faire passer les tests nouveaux puis la suite complète ;
5. mesurer la version nouvelle avec le même protocole ;
6. produire un tableau avant/après ;
7. analyser toute régression supérieure aux seuils ;
8. ne fusionner qu’après satisfaction du critère de sortie.

Une amélioration fonctionnelle ne justifie pas de supprimer un test existant.
Un seuil de performance ne doit être relâché qu’avec une raison documentée dans
le rapport de l’étape.

### 11.1 Compte rendu obligatoire après chaque étape

est réalisée seulement quand son journal, à la section 28, contient :

- intervalle de confiance pour les mesures ciblées ;

## 22. Protocole de performance

### 22.1 Règles de mesure

Les résultats avant et après doivent être pris :

- sur la même machine et le même mode d’alimentation ;
- avec les mêmes versions de Python et dépendances ;
- avec les mêmes jeux de données générés et leur graine ;
- sans réseau Internet, sauf test explicitement réel ;
- avec la graine de référence 20260813 ;
- après trois passages de chauffe ;
- sur vingt passages pour les mesures courtes ;
- sur au moins cinq passages pour les scénarios lourds ;
- en conservant médiane, p95, minimum, maximum, écart-type et coefficient de
  variation ;
- avec un intervalle de confiance bootstrap à 95 % pour toute amélioration
  revendiquée ;
- avec time.perf_counter_ns pour le temps ;
- avec mémoire RSS maximale de tout l’arbre de processus et, si utile,
  tracemalloc ;
- avec nombre d’appels HTTP, octets lus/écrits et taille du stockage ;
- en JSON brut plus un résumé Markdown.

Une comparaison est invalide si l’environnement ou le jeu de données diffère.
Elle est également invalide si le résultat fonctionnel est incorrect. Une
campagne est rejouée si le coefficient de variation dépasse 5 % sans cause
expliquée.

Pour une zone non ciblée par l’étape, la médiane ne doit pas régresser de plus
de 5 %, et le p95 ou la RSS de plus de 10 %. Une amélioration n’est déclarée que
si son intervalle de confiance confirme le seuil annoncé.

## 25. Stratégie de migration et retour arrière

Toute migration d’état doit :

1. refuser un schéma source inconnu ;
2. créer une sauvegarde nommée et datée ;
3. écrire la cible dans un nouveau fichier ;
4. valider le nombre d’entrées, tombstones et chemins ;
5. remplacer atomiquement seulement après validation ;
6. être idempotente ;
7. conserver la sauvegarde jusqu’à une release suivante ;
8. fournir un outil de diagnostic ou d’export ;
9. ne jamais déplacer ni supprimer un média pendant la migration du registre.

Le rollback de code doit être documenté si l’ancien programme ne sait pas lire
le nouveau format. Un export JSON version 1 en lecture seule peut servir de
pont, sans redevenir la source de vérité.

#### Travail effectué

- le registre migre de v1 vers v2 de façon additive et idempotente ; anciennes
  clés et archives restent lisibles, et le JSON v1 d'origine est conservé dans
  `.blink_download_state.v1.backup.json` avant la première écriture v2 ;
- identité source et corrélation inter-source sont séparées : l'USB ignore l'ID
  renuméroté du manifeste, le cloud conserve son ID distant, et réseau/module/
  caméra stable empêchent les collisions multi-réseaux et multi-hubs ;
- le nom API brut sert au repli d'identité ; `safe_name` ne sert plus qu'aux
  chemins. Les composants Windows réservés, séparateurs et longueurs sont
  neutralisés, puis une empreinte SHA-256 courte distingue les valeurs qui
  deviendraient identiques après assainissement ;
- `entry.path` est l'autorité pour un acquis : chemin relatif obligatoire,
  contenu sous `output`, fichier ordinaire, taille non nulle et taille enregistrée
  cohérente. Un média absent/tronqué est réparé ; une tombstone reste prioritaire,
  y compris avec `--overwrite` ;
- la fusion JSON force une version monotone et empêche une copie downloader
  périmée d'annuler une exclusion concurrente. La transactionnalité complète et
  le remplacement du verrou restent volontairement à l'étape 3 ;
- le rapprochement USB/cloud est symétrique, bijectif et de cardinalité maximale.
  Il emploie un index temporel `bisect` et Hopcroft-Karp itératif ; le passage USB
  apparie désormais le lot entier au registre et consomme chaque match une fois ;
- un index éphémère du registre et de ses chemins accélère les vérifications. Il
  n'est jamais sérialisé et est invalidé par les helpers d'écriture ;
- le cloud utilise le `network_id` propre à chaque clip et le filtre caméra
  compare le nom original, de sorte que `A/B` ne sélectionne pas `A_B` ;
- `.github/workflows/ci.yml` exécute désormais `test_stage2_identity.py` dans la
  matrice Windows/Linux/macOS × Python 3.11/3.12.

Limite documentée : blinkpy 0.25 n'expose pas toujours `device_id` ni
`network_id` sur les objets USB. Dans ce cas, la corrélation se replie sur le nom
API original ; un renommage USB ne peut donc pas être reconnu avec certitude.
